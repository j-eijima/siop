# 仕様書

[English](README.md) | **日本語**

アプリが何をするか、どこまでできたら受け入れかを、たまたまそれを実装しているコードから切り離して置く。
このプロジェクトは一つのプロトコルを何度も実装するので、仕様書は「別の言語で作り直しても
残るべき部分」にあたる。

読み手は、これから手で動作を確かめる人と、これから振る舞いを変えるコーディングエージェント。
ここにあるのは観察できる振る舞いの約束であって、クラスの説明ではない。

## ここに書くもの

- 人が見て判断するしかない振る舞い。画面が何を出すか、何と書くか、トークンに署名する前に
  ユーザーが何を見ていなければならないか。
- 合意しただけでまだ作っていない要件。各仕様書は現状を明記し、未実装の約束を現状の説明と
  取り違えないようにする。
- 実装をまたいで同一であるべき振る舞い。プラットフォームの都合で本当に違う場合は、
  どれがどう違うかを書く。

## ここに書かないもの

- テストが単独で判定できるもの — 署名、サムプリント、クレームの検査、RP 側の 7.5 の検証。
  それらはルートの [README](../../README.ja.md) が挙げるスイートにあり、仕様書に写すと
  誰にも気づかれずに古くなる。
- なぜその設計にしたか。それは決定記録で、[../decisions/](../decisions/) に置き、
  コーディングエージェントのスキルが持つ目次から、作業に関係するものだけを読ませる。
- 進捗、ビルド手順、どのクラスが何を実装しているか。それは README。

## 書き方

- 主題ごとに 1 ディレクトリ。他のディレクトリと同じく `README.md` と `README.ja.md` を置く。
- 人が順にたどる振る舞いは **振る舞い** の節に、`gherkin` のコードブロックで書く。
- 常に成り立つ要件と、起きてはならないことは **制約** の節に、EARS の一文ずつで書く。
  `The <system> shall <response>`、または `When <trigger>, …` / `While <state>, …` /
  `If <trigger>, then …` / `Where <case>, …`。Gherkin は「起きない」ことを書けても、
  それをいつ確かめるのかを書けない。「鍵が作られていない」のようなステップが
  検証不能になるのはそのため。
- 同じ要件を両方の形で書かない。`When` を無理に付けた規則に見えるシナリオは、制約の側。
- Gherkin のキーワードと EARS の文は両言語とも英語のまま。それ自体が成果物であって、
  それについての散文ではない。日本語版は周りの文を訳し、各制約に括弧で訳を添える。
- 手で実際に確かめるものだけに絞る。網羅した仕様書は読まれなくなり、読まれない仕様書は
  無いより悪い。
